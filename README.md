# C11Bank
>This readme was generated by ai.

A console-based bank management system written in C++. Staff members log in with a username and password, and what they can do depends on the permissions assigned to their account. They can manage bank clients, perform deposits and withdrawals, and administer other staff accounts. All data is stored in plain text files, so there are no external dependencies.

The project is built around a clear three-layer architecture (UI, business logic, data) and is meant to show object-oriented design in C++: inheritance, templates, polymorphism, etc.

---

## Features

**Clients**
- List all clients (account number, name, PIN, phone, balance)
- Add, update, delete, and find a client by account number
- Account numbers are unique

**Transactions**
- Deposit and withdraw, each with a confirmation step
- Negative amounts are rejected; withdrawals cannot exceed the balance
- Total Balance screen: per-client balances plus the bank-wide total (also written out in words)

**Users and permissions**
- Log in with a username and password
- List, add, update, delete, and find staff users
- Fine-grained permissions per user (see [Permissions](#permissions))
- Usernames are unique
- A built-in `admin` account that cannot be created, edited, or deleted through the app, so the system can never be locked out of user management

**General**
- Every change is saved to disk immediately
- Screens that need a permission the user does not have show an access-denied message instead of failing

- The project targets the `v145` platform toolset and C++20. If you have a different toolset installed, retarget it under **Project > Properties > General > Platform Toolset**

### Build and run

1. Open `C11Bank.slnx` in Visual Studio.
2. Select the **x64 | Debug** configuration.
3. Press **Ctrl+F5** (Start Without Debugging).

> **Important:** the program reads `Clients.txt` and `Users.txt` from its *working directory*. Visual Studio uses the project folder by default, which is where these files live. If you launch `C11Bank.exe` from somewhere else, make sure both files are in the folder you launch from. Without a `Users.txt` there are no accounts to log in with, and the app cannot create the first one for you.

## Permissions

Each user has one integer, `Permissions`, that acts as a bitmask. Every permission is a single bit, and a user has a permission when that bit is set (`(Permissions & Permission) == Permission`).

| Permission | Value | Gate |
|---|---|---|
| List Clients | 1 | Show Clients List screen |
| Add New Client | 2 | Add New Client screen |
| Delete Client | 4 | Delete Client screen |
| Update Client | 8 | Update Client screen |
| Find Client | 16 | Find Client screen |
| Transactions | 32 | The whole Transactions menu (deposit, withdraw, total balance) |
| Manage Users | 64 | The whole Manage Users menu |
| **All** | **-1** | Every bit set, so every permission |

Combine permissions by adding their values. For example, `3` is List + Add, and `96` is Transactions + Manage Users. When you add or update a user, the app asks a series of yes/no questions and builds this number for you.

## Architecture

```
+-----------+     +--------------+     +------------+     +-----------------------+
| UI Layer  | --> | Middle Layer | --> | Data Layer | --> | Clients.txt/Users.txt |
| screens   |     | entities and |     | load/save  |     +-----------------------+
| and menus |     | managers     |     |            |
+-----------+     +--------------+     +------------+
```

Each layer is designed to talk only to the one below it. For example, a deposit flows like this:

`clsDepositScreen` -> `Clients.DepositTo()` -> `clsClientManager::_Deposit()` -> `Save()` -> `clsData::Save()` -> `clsClientsData::SaveDataToFile()` -> `Clients.txt`

### Design notes

- **Inheritance:** `clsClient` and `clsUser` both extend `clsPerson`. Screens follow the same idea: `clsScreen` -> `clsClientScreen` / `clsUserScreen` -> concrete screens.
- **Generic manager:** `clsManager<T>` holds the list of objects and the shared save logic. `clsClientManager` and `clsUserManager` only add what is specific to each type.
- **generic data manager:** `clsClassData<Derived, Entity>` implements load and save once. Each derived class (`clsClientsData`, `clsUsersData`) only supplies `ConvertLineToObject` and `ConvertObjectToLine`.
- **Null object:** `EmptyObject()` and `IsEmpty()` are returned instead of null pointers, so a failed lookup is safe to use.
- **Object modes:** each entity carries a mode (`_EmptyMode`, `_AddNewMode`, `_UpdateMode`) that decides how a save is handled.
- **RAII session:** the login screen creates a local `clsSession`. When the user logs out and the function returns, its destructor clears the current user.
- **Bitmask permissions:** one `int` per user holds all permissions (see above).

## Data files

Both files are plain text with one record per line and fields separated by `#//#`.

**`Clients.txt`**

```
FirstName#//#LastName#//#Email#//#Phone#//#AccountNumber#//#PinCode#//#Balance
Sara#//#Khalil#//#sara@example.com#//#0501234567#//#A100#//#4321#//#2500.000000
```

**`Users.txt`**

```
FirstName#//#LastName#//#Email#//#Phone#//#Username#//#Password#//#Permissions
Omar#//#Nasser#//#omar@example.com#//#0507654321#//#omar#//#pass123#//#3
```

The files are rewritten in full after every change. Fields cannot be empty or contain the separator `#//#`, and if you edit a file by hand, keep every line in exactly this shape.

## Known limitations

This is a learning project and is not suitable for real banking data.

- **Plain-text credentials.** Passwords and PINs are stored unhashed in the text files and shown on the user and client screens.
- **Single-word input.** Text fields are read with `cin >>`, so only the first word is kept ("Mary Ann" is saved as "Mary").
- **Protected `admin`.** The `admin` account cannot be edited through the app, so changing its password means editing `Users.txt` by hand. The app also cannot create it; the row must exist in `Users.txt`.
- **No history.** There is no transaction log, login log, or transfer between accounts.
- **Single instance.** Data is kept in memory and rewritten wholesale on every change, so run only one copy of the program at a time.
- **No automated tests.**
- **Screen clearing** uses ANSI escape codes, so use Windows Terminal or a console with virtual terminal support.
